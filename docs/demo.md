# Черновик сценария демо — 5 минут

Демо показывает уже работающие расчёты и выгрузки. Интерфейс `ui/app.py` пока общий интерфейс харнеса, а специализированный экран графа и инструмент `graph_tools` отсутствуют. Поэтому три узла ниже разбираются в терминале по реальному `outputs/nodes_roles.csv`; вопросы AI-ассистенту по графу — заготовки для запланированной интеграции, они не выдаются за проверенную возможность текущего приложения. Такой fallback позволяет объяснить реальные узлы, но **не закрывает must-have экран схемы сети**: для полного демо перед выступлением потребуется подключить визуализацию и отрепетировать её.

## Подготовка окружения

Команды выполняются из корня репозитория. Для самого пайплайна достаточно Python и пакетов ниже; GPU и API-ключи ему не нужны. Установка пакетов через `pip` требует доступа к пакетному индексу.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-pipeline.txt
python3 run_pipeline.py
```

Эти команды готовят и запускают детерминированную часть демо. Для запуска общего AI-харнеса вживую потребуется дополнительно `pip install -r requirements.txt`, настроенный провайдер в локальном `.env` и рабочий API-ключ; это само по себе не подключит к нему графовые данные. Smoke test харнеса использует подменённый HTTP-сервер и тестовые ключи, так что его успешный результат подтверждает тестовый цикл, а не доступность живого провайдера. Подготовка UI не является частью этого сценария, пока графовая визуализация и `graph_tools` не интегрированы.

### 1:00–3:30 — три разбора по CSV

Пока специализированной визуализации сети в UI нет, показать поиск в CSV приведённой выше командой. Значения ниже взяты из `outputs/nodes_roles.csv` и `outputs/top_nodes.csv`.

1. **Координатор, `gid=100000000331309100`, `rule=C1`** — приоритет 0.9907, роль coordinator, 5 плательщиков и 99 получателей, 984 635 ₸ входящих и 23 001 375 ₸ исходящих, 3 seed в двух шагах выше. Поле evidence формулирует посредничество как «выше 99% узлов»; правило C1 требует значения в верхних 5% betweenness и не менее 5 входов и выходов. [Правило C1 в критериях ролей](roles.md#критерии-ролей).

2. **Консолидатор, `gid=100000000332284100`, `rule=K1`** — приоритет 0.8418, 10 плательщиков, входящие 107 426 ₸, исходящие 289 500 ₸, 3 получателя. K1 срабатывает при пяти и более разных плательщиках; превышение исходящей суммы над входящей отмечается как возможные поступления из-за пределов выгрузки, а не как установленный факт. [Правило K1 в критериях ролей](roles.md#критерии-ролей).

3. **Узел на границе выгрузки, `gid=100000000018102100`, `rule=P-trunc`** — периферийный, глубина 4, получил 7 000 ₸ от одного плательщика; исходящие отсутствуют в выгрузке. P-trunc присваивается после проверки более ранних правил и означает, что на четвёртом колене исходящие не наблюдались. Это не доказывает, что узел конечный; рекомендуется дополнительная выгрузка. [Правило P-trunc в критериях ролей](roles.md#критерии-ролей).

Подчеркнуть, что выбранные строки — фактические примеры из текущих CSV. Топовый координатор рейтинга — другой GID (`100000003684369100`, приоритет 1.0); для трёхминутного разбора выбран координатор с полным набором наглядных метрик из одного CSV.

## Пять вопросов жюри

1. **Почему такие пороги?** Их выбрали по распределению этой выборки: например, ≥5 плательщиков встречается примерно у 2% узлов, а ≥10 получателей — у 3%. Это эвристики для сортировки аналитической проверки; их следует калибровать и валидировать на размеченных данных.
2. **Как отличаете обрыв выгрузки от настоящего конечного узла?** Для узлов 1–3 колена без исходящих ≥5 000 ₸ обход не оборвался, поэтому при выполнении порога суммы или числа плательщиков возможен E1. На 4-м колене исходящие не наблюдались: если более раннее правило не назначило роль, узел получает P-trunc. В этой выгрузке P-trunc присвоен 444 узлам; это метка неполноты наблюдения, а не доказательство конечного получателя.
3. **Почему Louvain работает с ненаправленным графом?** Для поиска плотных групп направление сворачивается, а вес связи равен сумме переводов. Ролевые признаки и центральность при этом считаются на направленном графе.
4. **Что изменится на миллионе узлов?** Нужны более производительная графовая библиотека или графовый движок, приближённая центральность, обработка компонент параллельно, инкрементальный пересчёт и хранение в графовой БД.
5. **Как избежать обвинительных формулировок?** Говорить о признаках и гипотезах для проверки. Нет ground truth и клиентских атрибутов, а наблюдаются только исходящие переводы; оценка приоритета не является доказательством нарушения.
